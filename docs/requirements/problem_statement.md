# Problem Statement (draft)

## Context

When a course registration period opens, every student tries to register at the same moment. University registration systems we have used fail at exactly that moment: the server stops responding beyond a certain number of concurrent students, and students cannot tell whether their registration went through.

This project builds a new registration system designed for that moment.

## Who has the problem

- **Student** (main actor): needs to get a seat in the classes they want, and needs a clear, trustworthy answer about whether they got it.
- **System admin**: sets registration up before it opens (creates classes, sets the registration period). The admin is not under pressure during the peak.

## The problem

At the opening of a registration period, **2,000+ students** send registration requests **at the same moment**. Under this spike, a registration system must still answer every request **correctly**. Being slow is acceptable; being wrong is not.

## What the system must guarantee

| # | Guarantee | Meaning |
|---|---|---|
| G1 | No overbooking | A class never has more registered students than its capacity, even when many requests compete for the last seat. |
| G2 | No lost registration | Once a student is told "registered", the seat is theirs and survives crashes and restarts. |
| G3 | No duplicates | Retrying or double-clicking registers a student at most once per class. |
| G4 | Clear answer | Every request ends as registered, rejected (with a reason) or "busy, retry". It is never left unknown. |
| G5 | Degrade safely | Under overload the system may slow down or ask students to retry, but never breaks G1–G4. |

When reliability (G1–G4) conflicts with availability at peak load, **reliability wins**.

## Scope

### In scope

**Student**

- Browse open classes and their remaining seats.
- Register for one or more classes in a single request. Each class is accepted or rejected independently; a rejected class does not cancel the others.
- Drop a registered class while the registration period is open. The seat is freed immediately for other students.
- View their own registrations (needed to confirm the outcome after a timeout or "busy, retry").

**Registration rules** (checked per class at registration time)

- Seat available (capacity not reached).
- No timetable clash with the student's other registered classes.
- Total registered credits do not exceed a fixed limit defined in code.
- Registration and drop are only allowed while the registration period is open.

**System admin**

- Create classes (title, credits, capacity, schedule). The class ID is generated by the system.
- Set the registration period (open and close time). There is one period for all students.

### Out of scope

- Courses (grouping classes under a course), semesters and multiple registration periods.
- Closing or editing a class while registration is open.
- Swapping classes, waitlists.
- Prerequisites, minimum credits, per-student credit limits.
- Payment, grades, timetable generation, notifications.
